## Direct byte and relocation evidence

The original PE `.rdata` window `0x4d42f0..0x4d4494` is 420 bytes (SHA-256 `45d46c4925394a64f263c910f6ab7826e2e321d974a920cb240f62d8b8e76dd6`). It starts with `ads.csv` and ends with the `00 fe ff 46` float read by `fldads_get_random_ad`. Relative to the window start, the original cached-log string is at `+0xbf`, download log at `+0xd9`, URL at `+0xf0`, error at `+0x118`, summary at `+0x17c`, and float at `+0x1a0`. The original debug-line map independently puts the cached log at line 225 before download at line 231, despite download machine code being earlier on the fallthrough path. The PE window is a content/order observation, **not** proof of the complete historical COFF contribution boundary.

The current-order control COFF `.rdata` is also 420 bytes, with float at `+0x1a0`, but cached comes **after** download/URL/error/summary (`+0x185` versus download `+0xbf`). `fldads_get_random_ad` is strict `FUNCTION_MATCH`; `fldads_threadmain` fails its content-mapped literal targets. The `fldads_update_local_adimg` move makes `fldads_threadmain` strict `FUNCTION_MATCH` with all 15 relocations and three direct transfers resolved, but its COFF `.rdata` becomes 416 bytes: cached `+0x181`, download `+0xbd`, float `+0x19c`. `fldads_get_random_ad` retains the same 192-byte instruction sequence except its float-address operand at `+82..84`; the report cannot independently map `.rdata+0x19c` to historical `0x4d4490`. The local `181r.csa` and `182r.peephole2` function dumps are identical after path/pointer normalization in the paired control and moved branch. Sources: [control comparison](../research-20260923-fld-context/current-order-control-comparison.json), [moved comparison](../research-20260923-fld-context/move-update-local-only-comparison.json), [mechanism report](../research-20260923-fld-context/fldads-get-random-ad-context-mechanism.json).

The four-byte drift is part of literal-pool ordering/packing, not a demonstrated missing 4-byte source constant. Both candidate pools keep cached last; the original PE window has cached before download and summary immediately before the aligned float. A padding insertion would mask this source-order discrepancy and is not supported. The float byte pattern occurs six times in the PE, so content alone cannot assign the moved relocation to this historical address.

## Bounded next discriminator and missing proof

The only evidenced source direction is **cached-log lexical order before download-log**, backed by historical lines and PE literal order. Three cache-first/guard/goto source variants already retain the current 420-byte pool order or damage the 223-byte target body; do not repeat equivalent syntax. For any genuinely new source-backed full-TU hypothesis, require in one report: `fldads_threadmain` strict match, preservation of all 11 exact peers, and an independently resolved `fldads_get_random_ad` float relocation. Compare the full candidate `.rdata` string sequence against the original 420-byte PE window rather than the float offset alone.

If a new form changes neither the tree literal order nor final `.rdata`, stop. A byte-neutral diagnostic compile of the existing cache-first variant with tree dumps and saved assembler can determine whether GCC retains cached-first source order before RTL but emits literals in optimized block order; this is a compiler-mechanism test, not a promotion candidate. The stronger missing artifact is the original `fld_adspot.o` or historical link-map/section-contribution evidence that binds the entire PE window and repeated float to this CU. Without it, the original PE and DWARF do not prove a section-relative float owner for the 416-byte candidate.
